### 第一组：理解 First-Fit 连续物理内存分配算法

**用户提示词：**

我负责 Lab2 的 First-Fit 分析和 Best-Fit 实现，队友已经完成 `page_init()`。请结合 `kern/mm/default_pmm.c`，解释 `default_init()`、`default_init_memmap()`、`default_alloc_pages()` 和 `default_free_pages()` 的作用。说明空闲块如何组织、分配时如何拆分、释放时如何合并，并分析 First-Fit 是否有改进空间。

**AI 回答：**

First-Fit 使用按地址顺序排列的双向链表管理空闲物理内存块。每个空闲块由首页的 `Page` 描述符代表，`property` 表示块内页数，`nr_free` 表示全部空闲页数。

1. `default_init()` 初始化链表头，并将空闲页计数清零。
2. `default_init_memmap()` 接收 `page_init()` 注册的可用页，清除保留状态，将空闲块加入链表。
3. `default_alloc_pages()` 从链表头开始，选择第一个足够大的空闲块；如果块大于申请大小，分配前面的页面，将剩余部分放回链表。
4. `default_free_pages()` 将释放区间按地址顺序插回链表，检查并合并与它相邻的前后空闲块，同时恢复空闲页计数。

例如，按地址顺序有 10、4、8 页三个空闲块，申请 3 页时，First-Fit 会选择首先遇到的 10 页块。

该实现最坏需要遍历整个空闲链表。可以使用索引、平衡树或其他组织方式改进查找效率；及时合并相邻空闲块可以缓解外部碎片，但不能将被已分配页面隔开的空闲块直接合并。

### 第一组：设计并实现 Buddy System 分配模块

**用户提示词：**

我负责 Lab2 的任务三：Buddy System 伙伴系统分配算法。请参考当前 ucore 的物理内存管理框架，分析 `pmm_manager` 接口、`struct Page`、`Page.property`、`PG_property`、`page_link`、`alloc_pages()` 和 `free_pages()` 的使用约定。

请在不破坏现有内核接口的前提下，设计并实现 Buddy System，要求：

1. 使用多个 order 空闲链表管理大小为 `2^order` 页的空闲块；
2. 实现初始化、物理内存初始化、页分配、页释放、空闲页统计和检查接口；
3. 初始化时将连续物理页范围分解为满足地址对齐条件的二次幂块；
4. 分配时将请求页数向上取整到能够容纳请求的最小 order；
5. 如果对应 order 没有空闲块，则从更高 order 获取块并逐级拆分；
6. 释放时根据物理页号和异或规则计算伙伴地址；
7. 当伙伴处于空闲状态且 order 相同时，逐级合并为更高 order 的块；
8. 正确维护 `Page.property`、`PG_property`、空闲链表和空闲页总数；
9. 说明非 2 的幂次请求的分配和释放规则；
10. 保留现有的 `pmm_manager` 接口和内核测试约定。

请先分析数据结构、初始化、分配、拆分、释放和合并过程，再给出实现方案，并说明可能的边界条件。

**AI 回答：**

Buddy System 将空闲物理页按照 order 分组管理，order 为 k 的空闲块包含 `2^k` 个连续物理页。实现中可以为每个 order 建立一个空闲链表，并使用空闲块首页的 `Page` 描述符记录块的阶数。

初始化时，需要根据可用物理页的起始页号和剩余页数，选择满足地址对齐条件的最大块，并不断将剩余区域继续分解。这样即使可用页数不是 2 的幂，也可以用多个不同 order 的块表示。

分配时，先将请求页数向上取整到最小的二次幂。如果目标 order 没有空闲块，就从更高 order 的链表中取出一个块，并逐级拆分。每次拆分后，一半继续用于分配，另一半加入低一级的空闲链表。

释放时，根据：

```text
buddy_pfn = pfn ^ (1 << order)
```

计算伙伴页号。如果伙伴存在、order 相同并且处于空闲状态，则将伙伴从链表中移除，与当前块合并为更高 order 的块，再继续检查更高阶伙伴。

由于 Buddy 分配会向上取整，申请 3 页时实际分配 4 页，释放时必须按照实际块大小释放：

```c
page = alloc_pages(3);
free_pages(page, 4);
```

实现后应通过 `pmm_manager` 接口接入内核，并通过编译和 QEMU 输出确认实际使用的是 Buddy System。

### 第三组：修复 Buddy 块合并时的状态标志问题

**用户提示词：**

Buddy System 在块拆分和合并测试中已经能够完成分配和释放，但需要检查块合并后页面状态标志是否正确。请分析合并过程中旧块头的状态可能产生什么问题，并给出不破坏现有链表和页面状态的修复方法。

**AI 回答：**

Buddy 块合并时，两个低阶块会被移出原来的空闲链表，并由较低地址的块头表示合并后的高阶块。如果旧伙伴块头上的状态标志没有清理，后续检查可能错误地认为该页面仍然是已分配块头，或者将已经失效的块头误认为有效空闲块。

因此，合并时需要：

1. 从原 order 的空闲链表中移除伙伴；
2. 清理旧伙伴块头的 `Page.property` 和相关状态；
3. 清除不再作为已分配块头的 `PG_buddy_allocated` 标志；
4. 在合并后的低地址块头上设置新的 order；
5. 设置新的 `PG_property` 状态；
6. 将合并后的块加入更高 order 的空闲链表。

本次实现中针对状态残留问题加入了：

ClearPageBuddyAllocated(base);
