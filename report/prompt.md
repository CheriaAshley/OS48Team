## 第一组：物理内存初始化任务分析

**用户提示词：**

我负责 Lab2 的 `page_init()`，请结合实验指导书，分析物理内存初始化需要完成哪些步骤。说明 `pages`、`npage`、`va_pa_offset` 的作用，以及 `page_init()` 与 `pmm_init()` 的关系，按照实际代码执行顺序进行讲解。

**AI 回答：**

`pmm_init()` 是物理内存管理的初始化入口，首先通过 `init_pmm_manager()` 初始化内存管理器，再调用 `page_init()` 建立物理页管理结构，最后执行 `check_alloc_page()` 检查分配器。

`page_init()` 主要完成：

1. 使用设备树获取物理内存范围。
2. 计算物理页数量 `npage`。
3. 设置虚拟地址与物理地址的转换偏移量 `va_pa_offset`。
4. 建立 `pages` 描述符数组并初始化页面状态。
5. 排除内核和描述符数组占用的空间。
6. 使用 `init_memmap()` 注册可用物理页。

其中，`pages` 用于记录物理页状态，`npage` 表示物理页编号上界，`va_pa_offset` 用于内核虚拟地址和物理地址之间的转换。

## 第三组：定位 Sv39 分页启动异常

**用户提示词：**

我已经完成 `page_init()`，但是运行 QEMU 后只显示 OpenSBI 信息，无法进入内核。GDB 显示执行 `csrw satp, t0` 后，`satp` 变成 `0x8000000000080205`，随后无法访问 `0x80200038`。请结合 Sv39 页表机制分析原因，并给出具体的调试指令。

**AI 回答：**

`0x8000000000080205` 表示已经启用 Sv39 分页模式，根页表物理地址为 `0x80205000`。

问题可能是启动页表没有映射 CPU 当前执行的低虚拟地址，导致开启分页后无法继续取指。

建议使用以下 GDB 命令检查页表：

```gdb
p/x $satp
monitor xp /1gx 0x80205010
monitor xp /1gx 0x80205ff8
```

检查根页表第 2 项及第 511 项是否有效。

如果第 2 项为 0，而第 511 项有效，说明启动页表可能只有高地址映射，缺少低地址恒等映射。

可以在 `entry.S` 中补充低地址映射，同时保留原有高地址映射。修改后重新编译，通过 GDB 和 QEMU 验证内核能否继续执行。

### 第一组：理解 First-Fit 连续物理内存分配算法

**用户提示词：**

我负责 Lab2 的 First-Fit 分析和 Best-Fit 实现，队友已经完成 `page_init()`。请结合 `kern/mm/default_pmm.c`，解释 `default_init()`、`default_init_memmap()`、`default_alloc_pages()` 和 `default_free_pages()` 的作用。说明空闲块如何组织、分配时如何拆分、释放时如何合并，并分析 First-Fit 是否有改进空间。

**AI 回答：**

First-Fit 使用按地址顺序排列的双向链表管理空闲物理内存块。每个空闲块由首页的 `Page` 描述符代表，`property` 表示块内页数，`nr_free` 表示全部空闲页数。

1. `default_init()` 初始化链表头，并将空闲页计数清零。
2. `default_init_memmap()` 接收 `page_init()` 注册的可用页，清除保留状态，将空闲块加入链表。
3. `default_alloc_pages()` 从链表头开始，选择第一个足够大的空闲块；如果块大于申请大小，分配前面的页面，将剩余部分放回链表。
4. `default_free_pages()` 将释放区间按地址顺序插回链表，检查并合并与它相邻的前后空闲块，同时恢复空闲页计数。

例如，按地址顺序有 10、4、8 页三个空闲块，申请 3 页时，First-Fit 会选择首先遇到的 10 页块。

该实现最坏需要遍历整个空闲链表。可以使用索引、平衡树或其他组织方式改进查找效率；及时合并相邻空闲块可以缓解外部碎片，但不能将被已分配页面隔开的空闲块直接合并。

可以保留按地址排列的空闲链表，方便释放时判断相邻关系；分配时遍历整个链表，使用 `best` 记录最小的可用候选块，遇到完全匹配的块时提前停止。

主要实现如下：
